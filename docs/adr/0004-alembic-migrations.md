# ADR-0004: Adopt Alembic for database migrations

**Date:** 2026-06-09

## Context

The schema was created with `SQLModel.metadata.create_all()` at app startup. That works exactly once: `create_all()` only creates *missing* tables — it never alters an existing one. The trigger was the `Submission` model (ticket #3), the second real schema change. The database is still immature and will keep changing, very likely *after* we deploy to production — and `create_all()` has no answer for evolving a table that already holds data.

We needed a controlled, versioned way to change the schema over time. Requirements:

- Versioned, ordered migration history (not "whatever `create_all` infers today")
- Reversible — every migration has a down path
- Low authoring friction — ideally derive migrations from the models we already define
- Safe against existing production data

## Options

| | `create_all()` at startup | hand-written raw SQL | Alembic |
|---|---|---|---|
| Versioned history | no | yes (by convention) | yes |
| Reversible (down-migrations) | no | manual, easy to get wrong | yes (up + down) |
| Generated from model metadata | n/a | no | yes (autogenerate) |
| Alters existing tables / prod data | no | yes | yes |
| Room for human error | low (but can't evolve) | high (every statement by hand) | low (autogen) + review |
| Coupling | SQLAlchemy | none | SQLAlchemy (by design) |

## Decision

**Adopt Alembic**, with migrations applied via `alembic upgrade head`, replacing `create_all()`.

Alembic is SQLAlchemy's twin — same maintainers, and it reads our SQLModel/SQLAlchemy metadata directly, so it can **autogenerate** an upgrade script by diffing the models against the live schema. That kills the messiness and per-statement error risk of hand-written raw SQL while giving us clean `upgrade`/`downgrade` paths. The one cost is that autogenerated scripts must be **reviewed** before committing — a small, worthwhile price for a schema history that is versioned, reversible, and documented.

## Consequences

- **Autogenerate is a hint, not ground truth.** Every generated migration is reviewed and often hand-edited. Autogenerate misses `server_default`, partial/conditional unique indexes, and the details of native enum types — these are added by hand.
- **Native Postgres enums need explicit `create`/`drop`.** Autogenerate emits an inline `sa.Enum(...)` that auto-creates the type on `upgrade` but leaves it orphaned on `downgrade`, breaking the next `upgrade`. The fix is an explicit `postgresql.ENUM(..., create_type=False)` with `.create()`/`.drop()` (`checkfirst=True`) in the migration. `create_type=False` is silently ignored on generic `sa.Enum`, so the PG-dialect type is required. An `upgrade → downgrade → upgrade` round-trip test enforces that migrations are actually reversible.
- **Migrations run out-of-band** (`alembic upgrade head` as a deliberate step), not at app startup — startup-time DDL would race across replicas.
- **Schema source of truth is the SQLAlchemy metadata.** The "twin" relationship that gives us autogenerate is also a coupling: leaving SQLAlchemy would mean leaving Alembic. Acceptable, given SQLModel/SQLAlchemy is already core to the stack.
- `create_all()` is removed from the startup path; contributors run migrations explicitly (documented in `COMMANDS.md` and `CONTRIBUTING.md`).
